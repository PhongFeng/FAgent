# 实施路线

## 当前状态

已有游戏制作流程提纲和 `godot/f-game/` Godot 项目骨架。本轮建立通用体系规划；尚未实施 Agent、Skill、自动化工具或核心玩法。游戏类型按用户选择暂不确定。

推进采用阶段验收，不先承诺与游戏规模、人员投入无关的完成日期。

## 阶段与验收

| 阶段 | 实际交付 | 验收依据 |
| --- | --- | --- |
| 0：体系规划（本轮） | Agent/Skill 边界、候选工具、任务协议、实施路线 | 范围清晰；实现状态与规划状态分开标注 |
| 1：工程基线 | 环境检查脚本、版本记录、可启动主场景、统筹/程序/QA 角色、四个基础 Skill | 从现有工程完成一次任务交接；导入、启动、图形检查有证据 |
| 2：最小可玩闭环 | 选定游戏类型后的核心操作、反馈、目标、失败或结束、重开 | 新用户按说明可启动，并独立走完一次游戏循环 |
| 3：垂直切片 | 小量完整内容、统一资源风格、音频、UI、必要的保存功能 | 有代表性的短流程可玩；关键缺陷处理；目标硬件达标 |
| 4：能力提炼 | 经真实任务改进的 Skill、可运行模板、宿主适配与使用说明 | 在独立工作区从新简报复用，记录需要人工修复的步骤 |
| 5：交付与分发 | 指定平台构建、示例、许可证与来源清单、版本说明 | 在约定的干净环境验证启动与关键路径，第三方可按说明复现 |

阶段 1 可在游戏类型确定前推进。阶段 2 开始前再确定 2D/3D、目标平台、核心玩法和资源风格，避免通用工具预先绑定某一类型。

## 近期实施顺序

1. **环境基线**：找到 Godot 标准版可执行文件，记录版本与导出模板，验证现有 `4.7` 项目配置。确定首个目标操作系统与渲染器。
2. **最小工程**：建立主场景和明确的启动反馈，验证导入、无窗口启动、图形运行。暂用自制占位资源。
3. **三个角色定义**：先实现 `producer`、`godot-engineer`、`qa`，使用同一份任务协议和证据格式。先顺序执行。
4. **四个基础 Skill**：实现 `game-brief`、`godot-bootstrap`、`godot-feature`、`godot-verify`，将实际重复的检查封装成脚本，验证宿主可发现与调用。
5. **试跑任务**：以“建立可启动主场景”为首项工程任务，再选择一个小功能完成需求、实现、验证、修复的闭环。
6. **选择首款游戏**：基于已跑通的工具链立项，设定核心循环、内容上限和验收标准，再加入资源与交付能力。

首个闭环完成后再决定是否需要自动调度器、多个并行 Agent、编辑器插件或更多宿主适配。用实际等待时间与失败原因决定投入方向。

## 其他用户的目标使用路径

这是待实现的体验目标，不是当前可用的安装流程：

1. 获取仓库，选择已支持的 Agent 宿主，安装明确列出的最小依赖。
2. 指定 Godot 路径、工程位置与输出位置，运行环境检查。
3. 提供游戏想法、目标平台和约束，由统筹生成简报及可验收任务。
4. 顺序或按已验证的并行策略执行任务，用户在关键玩法节点试玩并反馈。
5. 运行验证与导出，取得可玩的构建、源工程、资源归属记录及已知限制。

分发前提供一个可复现的完整示例。接入其他已有工程时先检查结构与依赖，不能直接覆盖已有配置。

## 如何判断复用有效

| 指标 | 记录方式 |
| --- | --- |
| 首次可玩耗时 | 从有效简报确认到用户首次完成核心循环；单列环境安装耗时 |
| 人工介入 | 记录每次介入的原因：需求决策、工具缺失、生成错误、体验调整 |
| 任务通过率 | 固定验收条件下首次通过的任务数 / 已验收任务数 |
| 复用成本 | 独立工程复用时修改了哪些步骤、参数与脚本 |
| 构建复现情况 | 记录环境、版本、命令、退出码和启动结果 |

首次完整试跑建立基线后再设定量化目标。保留失败记录，让 Skill 的改进来自实际问题。

## 后续需要明确的决策

- 游戏：类型、2D/3D、目标玩家、核心体验、内容规模。
- 平台：首个发布平台、输入设备、性能目标与导出要求。
- Agent 宿主：先适配哪个工具，是否要求全链路开源、本地运行或离线使用。
- 分发：仓库许可证、素材授权策略、模板与示例的发布方式。

这些决策在相应阶段落地；不阻塞本轮体系规划。
